# NightRecon Night Product Standard

This document is the product and development standard for every NightRecon Night.

White Night is the first product track required to prove the complete standard.
Red, Blue, Purple, Black, and future Nights should reuse the same development
shape while keeping their own domain engines, workflows, data, and specialist
capabilities.

## Product doctrine

Every Night must satisfy three equally important product pillars.

### 1. NightRecon stack capability

A Night must operate as a first-class member of the composed NightRecon platform.

Stack capability means more than installing beside another package. A Night must:

- use versioned shared-core contracts for engagement, authorization, scope,
  evidence, audit, stop state, capability discovery, and common identifiers;
- exchange information with peer Nights only through explicit contracts,
  services, events, or portable schemas;
- never require direct runtime imports from another Night engine;
- preserve provenance when consuming data generated by another Night;
- never treat imported evidence as authorization;
- remain independently installable, upgradeable, removable, and testable;
- expose its capabilities to the composed workspace without duplicating peer
  functionality;
- support a shared engagement/workspace identity while preserving ownership of
  Night-specific domain state;
- fail clearly and safely on incompatible schema or package combinations;
- pass composition tests for every supported Night combination.

A composed NightRecon installation should feel like one platform to the operator,
while remaining a set of independently versioned products internally.

### 2. Standalone capability and deployment parity

Every Night must also be a complete product when no other Night is installed.

For White Night this requires both:

- direct installation to a supported device or operating system; and
- a bootable White Night Live USB deployment.

Where a future Night has a meaningful field/offline use case, it should support
the same Live deployment model.

Standalone capability requires:

- the same Night application, Night engine, and shared-core packages used by the
  composed stack;
- no hidden dependency on another Night;
- local-first operation for the Night's core mission;
- offline capability for workflows that do not inherently require an external
  service;
- secure persistent workspace storage;
- backup, restore, migration, upgrade, rollback, and uninstall behavior;
- clear installation and deployment diagnostics;
- identical authorization, safety, evidence, and audit rules across direct
  install, composed stack, and Live deployments;
- reproducible release artifacts and deployment acceptance tests.

Deployment profiles are packaging and operating-environment choices. They must
not create separate forks of the Night's business logic.

### 3. Domain-leading specialist capability

A Night is not complete merely because it installs and interoperates.

Each Night must become a high-quality specialist product for its assigned role,
capable of producing the strongest practical evidence, data, decisions, and
reports that its role requires.

Each Night therefore owns a complete specialist workflow:

```
inputs
  -> validated domain data
  -> specialist analysis/orchestration
  -> evidence/provenance
  -> review and decisions
  -> actions where authorized
  -> outcomes
  -> reporting/export
  -> retest/follow-up
```

Domain excellence requires:

- a purpose-built domain model rather than generic fields;
- complete operator workflows from intake to final report;
- strong data validation, normalization, deduplication, and provenance;
- evidence-backed conclusions with uncertainty and limitations represented
  honestly;
- useful automation without hiding decision logic;
- human review or approval where the workflow requires it;
- high-quality search, filtering, correlation, timelines, and history;
- reproducible calculations and deterministic transformations where practical;
- professional reporting for technical, operational, and executive audiences;
- structured exports so data can be reused by other tools and Nights;
- domain-specific integrations that add evidence rather than silently changing
  authority;
- measurable quality, performance, completeness, and regression tests;
- comparison/benchmark labs where specialist-tool comparison is meaningful;
- no unsupported claims of certainty, coverage, exploitability, attribution,
  detection, remediation, or risk.

## Shared architecture rule

Every Night should converge on the following dependency direction:

```
Night application
      |
      v
Night specialist engine
      |
      v
NightRecon shared core
```

Peer Night engines sit beside one another, not underneath one another.

Shared core owns Night-neutral contracts and enforcement. A specialist engine
owns its domain. The application owns presentation, operator workflows, and
deployment wiring.

Cross-Night collaboration occurs through explicit shared contracts, never by
reaching directly into a peer engine's internals.

## Universal development tracks

Development of a Night should progress across three tracks in parallel.

### Track A — Specialist capability

Build the actual professional capability of the Night:

1. domain and terminology;
2. core data model;
3. specialist workflows;
4. evidence and provenance;
5. analysis and correlation;
6. operator decision support;
7. reporting and structured export;
8. integrations;
9. quality/benchmark coverage;
10. mature operational UX.

### Track B — Standalone product

Prove the Night remains independently useful:

1. independent package boundary;
2. clean standalone installation;
3. workspace/storage abstraction;
4. configuration and migration;
5. direct-device installation and upgrade;
6. backup/recovery;
7. Live build where applicable;
8. encrypted persistence;
9. offline operation;
10. production deployment hardening.

### Track C — NightRecon composition

Prove the Night works correctly in the stack:

1. capability registration;
2. shared engagement identifiers;
3. shared contract compatibility;
4. cross-Night evidence import with provenance;
5. cross-Night event/data exchange;
6. composed workspace presentation;
7. peer install/remove isolation;
8. mixed-version compatibility handling;
9. combined workflow acceptance;
10. full-stack regression and release gates.

No track may be treated as an optional afterthought.

## Standard maturity gates for every Night

### Gate 0 — Product contract

Before substantial implementation:

- define the Night's mission and ownership boundary;
- define what belongs in shared core;
- define prohibited peer dependencies;
- define standalone and stack deployment expectations;
- define acceptance criteria and evidence-honesty rules.

### Gate 1 — Package foundation

- independent application package;
- independent specialist engine package;
- explicit shared-core dependency;
- capability registry;
- isolated build/install/uninstall tests.

### Gate 2 — Core specialist domain

- versioned domain objects;
- deterministic validation;
- storage interfaces;
- lifecycle/state rules;
- import/export schemas.

### Gate 3 — Governance and safety

As appropriate to the Night:

- scope;
- authorization;
- approvals;
- roles;
- revocation;
- action budgets;
- emergency stop/freeze;
- audit;
- secret handling.

A Night may consume shared enforcement without duplicating it.

### Gate 4 — Evidence, data, and reporting

- provenance-preserving evidence model;
- data quality rules;
- tamper/integrity controls where needed;
- timelines/history;
- reusable structured exports;
- technical report;
- operational report;
- executive summary;
- limitations/coverage statement;
- report reproducibility tests.

### Gate 5 — Professional operator product

- coherent workspace;
- search/filter/correlation;
- dashboards appropriate to the Night;
- saved state and recovery;
- clear errors and diagnostics;
- accessibility and performance;
- complete workflows rather than disconnected features.

### Gate 6 — Standalone production path

- clean-device install;
- upgrade;
- rollback/recovery;
- uninstall;
- backup/restore;
- offline acceptance;
- secure local storage;
- release artifact verification.

### Gate 7 — Live deployment path

Where applicable:

- reproducible boot image;
- same versioned Night packages;
- UEFI boot;
- appliance session;
- Secure/Ephemeral/Recovery modes;
- encrypted persistence;
- reboot persistence verification;
- no unintended host-disk interaction;
- integrity/recovery;
- signed/offline updates;
- Secure Boot target;
- hardware/endurance matrix.

### Gate 8 — Stack composition

- install beside supported Nights;
- launch independently;
- shared engagement/workspace contracts;
- cross-Night evidence exchange;
- no evidence-derived authority;
- peer removal isolation;
- mixed-version failure handling;
- composed workflow tests;
- full-stack release matrix.

### Gate 9 — Specialist release acceptance

A Night reaches a mature release only when:

- its specialist workflows are demonstrably useful end-to-end;
- reports and exports meet professional quality expectations;
- evidence and limitations remain honest;
- standalone and stack modes behave consistently;
- applicable Live mode reaches deployment parity;
- performance and regression targets are measured;
- security hardening is documented and tested;
- release artifacts are reproducible/auditable;
- known limitations are explicit.

## White Night specialist roadmap

White Night's domain is engagement governance, authorization, evidence custody,
exercise control, coordination, and high-quality engagement/exercise reporting.

The completed White foundation already includes:

- independent White application and engine packages;
- engagement, scope, exclusions, contacts, roles, and ROE domain;
- deterministic policy compilation;
- approval workflow and revocation foundations;
- evidence custody, lineage, governed export, and tamper-evident audit;
- standalone/full-stack/Live architecture contracts.

The remaining White roadmap should be executed against all three product pillars.

### White Stage 1 — Deployment parity foundation

Current work.

- reproducible White Live image;
- x86-64 UEFI boot;
- installed White/shared-core package artifacts;
- boot/readiness verification;
- direct-install acceptance retained alongside Live;
- no fork of White domain logic.

Then:

- Secure Workspace mode;
- Ephemeral Session mode;
- Recovery & Integrity Check mode;
- LUKS2 persistent workspace;
- engagement reopen across reboot;
- prove ephemeral sessions leave no engagement state;
- safe shutdown/removal;
- update/recovery foundation.

### White Stage 2 — Exercise Director

White must support professional planning and control of exercises and authorized
engagements:

- exercise objectives and success criteria;
- phases, injects, milestones, dependencies, and timing;
- participants, teams, observers, controllers, and responsibilities;
- communication plans and escalation paths;
- scenario state;
- planned versus actual timeline;
- issue/decision log;
- facilitator notes;
- pause/resume/abort state;
- reusable exercise templates;
- after-action linkage.

### White Stage 3 — Mission Control

Provide a live operational control surface:

- current engagement and authorization state;
- active phases/tasks;
- approvals awaiting action;
- stop/freeze state;
- evidence flow and custody health;
- relevant Night capability/status summaries;
- important warnings and exceptions;
- timeline of material events;
- operator acknowledgements;
- emergency-stop management through shared-core authority;
- no control-plane view may manufacture authority for another Night.

### White Stage 4 — Evidence and information intelligence

Turn collected engagement data into dependable White-Team information:

- unified engagement timeline;
- evidence catalog and provenance graph;
- custody history;
- decision and approval history;
- scope-change history;
- issue/observation register;
- action/outcome linkage;
- evidence completeness checks;
- missing-evidence and conflicting-evidence indicators;
- structured tagging/classification;
- retention/export policy enforcement;
- searchable engagement history.

### White Stage 5 — Professional reporting

Reporting is a primary White capability, not an export afterthought.

Required report families:

- engagement plan / rules-of-engagement pack;
- authorization and approval record;
- executive engagement summary;
- technical engagement report;
- exercise controller report;
- after-action report;
- timeline report;
- evidence/custody report;
- decisions and exceptions report;
- lessons learned;
- remediation/action tracker;
- retest/follow-up report;
- metrics and coverage appendix.

Reports should support:

- reproducible generation from versioned data;
- references back to evidence and decisions;
- clearly separated observed facts, analysis, assumptions, and limitations;
- operator review before finalization;
- configurable organization branding/templates;
- HTML/PDF plus structured JSON/CSV where meaningful;
- comparison between planned objectives and achieved outcomes;
- redaction/classification handling;
- report-version history.

### White Stage 6 — NightRecon stack integration

- discover installed Night capabilities;
- consume shared evidence/contracts without peer-engine imports;
- correlate Red/Blue/Purple/Black outputs to White engagement objectives;
- show which Night produced each datum;
- preserve original timestamps and provenance;
- coordinate approvals and stop state through shared contracts;
- build cross-Night engagement timelines;
- produce combined reports without duplicating peer engines;
- prove White removal does not break peer Nights;
- prove peer removal does not corrupt White engagement history.

### White Stage 7 — Collaboration and operational maturity

- operator roles and least-privilege access;
- concurrent workspace rules;
- comments/annotations and review state;
- assignment and handoff;
- offline-safe conflict handling;
- backup/restore and archive;
- import/export packages for disconnected environments;
- health/diagnostic surface;
- migration tooling;
- audit review tooling.

### White Stage 8 — Production hardening and acceptance

- signed release/update artifacts;
- offline update bundles;
- SBOM;
- Secure Boot support target;
- hardware compatibility matrix;
- Live endurance testing;
- direct-install upgrade/uninstall matrix;
- stack combination matrix;
- performance and large-engagement tests;
- recovery drills;
- evidence/report reproducibility checks;
- security review and threat-model closure;
- complete White release acceptance dossier.

## Future Night roadmap rule

When a new Night is started, copy the structure of this standard, not White's
specialist features.

For each future Night define:

1. **What specialist problem does this Night own?**
2. **What data/evidence must it produce better than a generic platform could?**
3. **What complete professional workflow must it support?**
4. **What belongs in shared core instead of this Night?**
5. **How does it run completely standalone?**
6. **Does it require a Live/offline field deployment?**
7. **How does it compose with existing Nights without importing their engines?**
8. **What professional reports/exports must it produce?**
9. **How will quality, completeness, performance, and honesty be measured?**
10. **What acceptance evidence is required before release?**

The target is therefore not a collection of modules.

The target is a family of independently excellent specialist products that can
also compose into one NightRecon platform.
